# Home Screen Redesign — Design Spec

Date: 2026-08-07
Status: Approved
Scope: Personal fork of CrossPoint Reader for the Xteink **X4**.

## Goal

Rebuild the Home screen around the device's identity rather than around one
book cover. Three changes, in the order they were asked for:

1. The recent-book cover stops being the hero.
2. The menu becomes a tiered tile layout with room for entries that do not
   exist yet.
3. The Almanac mark gets a permanent home on screen, not just on the boot
   splash.

Chrome and layout only. No typography change, no new reading feature, no new
network behaviour.

## Why the cover has to go

`homeCoverTileHeight` is 400 on an 800px-tall screen
([AlmanacTheme.h](../../../src/components/themes/almanac/AlmanacTheme.h)), so
half the display is a single book cover. That was defensible when the fork was
a plain e-reader. It is not defensible now that the Home menu carries flight
tracking, and it is the largest reclaimable block on the screen.

The mark already exists as a 120×120 packed 1-bit array
([src/images/Logo120.h](../../../src/images/Logo120.h)), generated by
[scripts/generate_logo.py](../../../scripts/generate_logo.py), and is drawn
exactly once — on the boot splash. `SCOPE.md` lists identity ("the Instrument
theme, the mark, the boot and sleep screens") as in scope, so giving the mark a
permanent place is inside the fork's own rules rather than an expansion of them.

## Decisions

| Question | Decision |
|---|---|
| Hero slot | **Compact status panel** — mark, wordmark, battery. Not a book cover |
| Tile form | **Hybrid** — full-width Continue Reading, 2-column grid, full-width Settings |
| Navigation | **Stays 1-D**, reading order. No new button bindings |
| New entries | Continue Reading and Network |
| Layout contract | **`tileRect(index)`** replaces uniform-pitch `MenuRowLayout` for Home |

## Layout

Portrait 480×800. Tier offsets are fixed, so configuring an OPDS server never
moves an existing tile.

| Tier | y | Height | Contents |
|---|---|---|---|
| Masthead | 0 | 112 | Full-bleed black. Mark + wordmark left, battery right. Not selectable |
| Continue Reading | 124 | 92 | Full width, black fill, title + progress bar + percent |
| Grid | 228 | 3 rows × 128 | Two 217px columns, 14px column gap, 12px row gap |
| Settings | 648 | 92 | Full width |
| Button hints | 752 | 48 | Unchanged |

Horizontal: `contentSidePadding` (16) each side, so usable width is 448.
Grid tiles are `(448 − 14) / 2 = 217` wide at x = 16 and x = 247. Full-width
tiles are x = 16, w = 448.

The tiers sum exactly: 740 (Settings bottom) + 12 = 752 = `buttonHintsTop`.

### Two vertical variants

There is no recent book on a fresh install, and the Continue Reading tier is
then absent. That is the one composition change that moves tiles, so it is
defined explicitly rather than left to fall out of the arithmetic:

Grid tile height is **fixed at 128** in both variants, and the grid block is
**vertically centred** in the region between the tier above it and the Settings
tier.

| Variant | Region for the grid | Block height | Grid starts at |
|---|---|---|---|
| With a recent book | 228–636 (408) | 408 | 228 (exact fit) |
| No recent book | 124–636 (512) | 408 | 176 |

Fixing the tile height rather than stretching to fill keeps one number under
test across both variants, and centring avoids a 104px hole below the grid.
The masthead and Settings tiers never move in either variant.

### Why Settings gets its own tier

It is configuration rather than content, so separating it is defensible on its
own. It also happens to be what makes both menu sizes resolve to exactly three
grid rows:

| OPDS | Entries | Index 0 | Grid indices | Grid rows |
|---|---|---|---|---|
| Off | 7 | Continue Reading | 1–5 (five tiles) | 3 (2, 2, 1) |
| On | 8 | Continue Reading | 1–6 (six tiles) | 3 (2, 2, 2) |

A lone tile in the final row spans the full width rather than sitting in the
left column. Identical geometry in both states is far easier to test than a
layout that reflows, and it means toggling OPDS never moves an existing tile.

## The layout contract

`MenuRowLayout` describes a uniform single-column pitch: one `rowStep`, one
`rowHeight`, applied to every index
([BaseTheme.h:111](../../../src/components/themes/BaseTheme.h)). This layout has
three tiers of differing width and height, so that struct cannot express it,
and neither can the `rowTouch` call it feeds
([HomeActivity.cpp:287](../../../src/activities/home/HomeActivity.cpp)).

Rather than widen `MenuRowLayout` with a column count and per-tier heights, Home
moves to a per-index accessor:

```cpp
struct HomeMenuComposition {
  int tileCount;
  bool leadingWideTile;  // index 0 is Continue Reading, not a grid tile
};

virtual Rect tileRect(Rect menuArea, int index, HomeMenuComposition composition) const;
```

`leadingWideTile` is load-bearing, not decorative. Without it the rule "index 0
is full width" would make Browse Files full width on a device with no recent
book, because the theme cannot see `recentBooks`. `HomeActivity` builds the
composition once and passes the same value to drawing and to hit-testing, so
the two cannot disagree about it. Settings being the trailing wide tile is a
fixed property of this layout and needs no flag.

`drawButtonMenu` iterates indices and asks for each rect; `HomeActivity`
hit-tests by asking the same function and testing point-in-rect. One source of
truth for "where is tile N", which is the invariant
[75af40e8](../../../src/activities/home/HomeActivity.cpp) established when it
stopped `HomeActivity` re-deriving row geometry that the theme had already
decided. A rect list is also a strictly simpler contract than pitch arithmetic:
there is no step, no first-index, and no page to keep in sync.

Declared as a `BaseTheme` virtual with a uniform-row default (built on the
existing `getButtonMenuLayout`) and overridden in `AlmanacTheme`. That matches
the file's established pattern — `BaseTheme` already carries fourteen virtuals
that `AlmanacTheme` selectively overrides — and keeps the diff free of an
unrelated refactor of `UITheme::getTheme`'s return type.

`MenuRowLayout` and `getButtonMenuLayout` stay for now; nothing else is worth
disturbing in this change.

## Continue Reading

An earlier note in this session claimed flipping `homeContinueReadingInMenu`
would be a one-line change. That is no longer accurate and is retracted here:
the flag inserts `STR_CONTINUE_READING` as an ordinary menu entry
([HomeActivity.cpp:317](../../../src/activities/home/HomeActivity.cpp)), and
this design wants a bespoke wide tile carrying a progress bar.

The resolution keeps one index space rather than adding a tier outside the menu:

- `homeContinueReadingInMenu` becomes `true`, so the existing insertion code
  still puts the string at index 0 and the recent-books offset arithmetic at
  [HomeActivity.cpp:270-291](../../../src/activities/home/HomeActivity.cpp)
  keeps working unchanged.
- `tileRect(0)` returns the full-width Continue Reading rect.
- `drawButtonMenu` special-cases index 0 to draw the progress bar beneath the
  label.

Navigation and hit-testing therefore treat it as an ordinary tile. Only drawing
knows it is special.

When there is no recent book the existing code already omits the entry (it
guards on `!recentBooks.empty()`). `HomeActivity` then passes
`leadingWideTile = false`, index 0 becomes an ordinary grid tile, and the grid
uses the second vertical variant above.

## Navigation stays 1-D

The buttons are already fully allocated. `Button::NavNext` resolves to side
Down **or** front Right, and `NavPrevious` to side Up **or** front Left
([MappedInputManager.cpp:99](../../../src/MappedInputManager.cpp)), and Home
spends Back on Resume and Confirm on Select. There is no free directional input
for column movement, and splitting the side/front aliases to get one would
change muscle memory on every screen that uses `ButtonNavigator`.

So the grid is a visual arrangement, not a navigation model. Next advances
left-to-right then down, in reading order. `ButtonNavigator` and
`MappedInputManager` are untouched.

Touch, where present, hit-tests through `tileRect` and therefore gets true 2-D
selection for free.

## Icons

`GfxRenderer::drawIcon` plots every ink pixel with `drawPixel(..., true)`
([GfxRenderer.cpp:1250](../../../lib/GfxRenderer/GfxRenderer.cpp)), i.e. always
black, which is why `AlmanacTheme::drawButtonMenu` currently discards its
`rowIcon` callback — an icon would vanish on a selected tile's black fill.

It gains a defaulted parameter:

```cpp
void drawIcon(const uint8_t bitmap[], int x, int y, int size, bool state = true) const;
```

([GfxRenderer.h:228](../../../lib/GfxRenderer/GfxRenderer.h)) Backward
compatible, and with a single theme in the tree the blast radius is one call
site. Selected tiles pass `false` so the icon reads white on black, the same
convention `drawBatteryLightningBolt` already follows.

## The masthead mark

`drawImage` blits at the bitmap's native size; there is no scaling path, so the
112px masthead needs its own asset rather than a scaled `Logo120`.

`generate_logo.py` hardcodes `SIZE = 120`
([scripts/generate_logo.py:24](../../../scripts/generate_logo.py)) and its
header comment records that 120 was chosen so the compass rose's diagonal edges
land cleanly instead of stair-stepping. The script takes a `--size` argument,
and the chosen size is checked with `--preview` at 56 and 64 before being
committed. If neither renders cleanly at 1 bit, the fallback is to keep the
mark at 120 and make the masthead tall enough to hold it, trading grid height —
that trade is decided by looking at the preview, not in advance.

## Labels and i18n

Grid tiles are 217px wide, which is tight. The worst case across the 31
translation files is Kazakh's "Жуырда оқылған кітаптар" for
`STR_MENU_RECENT_BOOKS` — roughly 23 characters, which will not fit one line.

Labels therefore render through the existing
`UITheme::drawCenteredWrappedText` with `maxLines = 2`, which wraps only when
the text overflows and vertically centres the resulting block
([UITheme.h](../../../src/components/UITheme.h)). Truncation is not acceptable
here: "Recent Bo…" is worse than two lines.

`wrappedText` returns a `std::vector<std::string>`, so this allocates per tile
per render. Justified rather than silent: Home renders on input, not per frame,
and `BaseTheme::drawList` already does the equivalent per row via
`truncatedText`. Worst case is seven short-string vectors, transient, freed
before `displayBuffer` returns. No steady-state RAM and no new buffer.

The Network tile needs a new key — `STR_WIFI_NETWORKS` ("Wi-Fi Networks") is
the Wi-Fi scan screen's title, not a menu label. Add `STR_MENU_NETWORK` to
`english.yaml` and regenerate with `scripts/gen_i18n.py`; the other 30
languages fall back to English until translated.

## Testing

`test/home_menu_layout/` exists precisely because the last session shipped a
6th-tile overlap that no test caught. Its current premise — uniform rows, last
row bottom clears the hints bar — does not survive this layout, so it
generalizes rather than being deleted:

- Across all four compositions — OPDS off/on × recent book present/absent —
  iterate every index through `tileRect` and assert each rect sits inside
  `[menuTop, buttonHintsTop)`, inflated by `kMenuSelectionReserve`
  ([AlmanacTheme.h:87](../../../src/components/themes/almanac/AlmanacTheme.h))
  so the selection stroke is included exactly as the existing tests already do.
- Assert no two rects overlap.
- Assert the grid is 3 rows in all four compositions, which is what pins the
  "OPDS never moves a tile" property above.
- Assert that toggling OPDS alone leaves every surviving tile's rect
  byte-identical, and that dropping the recent book moves the grid to the
  second variant's origin and nothing else.

That is a stronger invariant than "the last row clears the bar", and it is what
keeps this bug class dead.

`pio run -e simulator` (native + SDL2, added by PR #11) gives real
`getTextWidth` measurements for the Kazakh case and renders the whole screen on
the host, so label overflow and the masthead mark are checked without flashing.

## Cost

Drawing code, one defaulted renderer parameter, one i18n key, one regenerated
logo asset. No new heap buffers, no new task, no steady-state RAM. Flash delta
is expected to be small but is reported as measured, not asserted — the app
partition is ~85% full.

## Verification

1. `pio run` clean, no new warnings; report RAM/Flash delta.
2. `ctest` green, including the generalized `home_menu_layout` suite.
3. `pio run -e simulator` for the label and mark checks above.
4. On device: Home with and without an OPDS server configured, with and without
   a recent book, confirming nothing collides with the hints bar and the serial
   log shows no `Outside range` from `GfxRenderer`.

## Out of scope

- Typography. UI fonts are baked into flash at every size and style.
- Any new activity. The Network tile opens the existing
  `NetworkModeSelectionActivity`.
- Landscape. Home renders in forced Portrait; both readers reset to Portrait in
  their own `onExit()`.
- Sleep and boot screens. They keep the 120px mark.
- Reworking `MenuRowLayout` for the screens that still use it.
