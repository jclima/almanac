# 2048 — Design Spec

Date: 2026-08-09
Status: Approved, not implemented
Scope: One turn-based puzzle activity, reachable from a new home tile, plus the
`SCOPE.md` amendment that authorises it.

## Why this exists at all

`SCOPE.md` listed "Interactive apps — games, calculators, notepads" as out of
scope. The owner decided to open that door deliberately rather than quietly, so
this spec carries the scope change with the feature.

The original request was broader: an emulator plus games. That was refused on
hardware grounds, and the reasoning is recorded here so the question does not
have to be re-litigated.

### Why no emulator fits

- **NES / Game Boy class.** Every working ESP32 port leans on PSRAM for the
  working set and a fast SPI LCD for output. The C3 has a single RISC-V core at
  160 MHz, no PSRAM, and ~380 KB of RAM already carrying the 48 KB framebuffer,
  the font tables, and the EPUB engine. They are also colour and per-pixel
  sprite, so every frame would owe a full-frame dither on a CPU that has no
  headroom for one.
- **Chip-8.** The honest edge case. It clears the two bars you would expect it
  to fail — 4 KB of RAM, and natively 1-bit monochrome. It dies on the other
  two: a 16-key hex keypad against our seven buttons
  ([HalGPIO.h:101](../../../lib/hal/HalGPIO.h)), and real-time gameplay against
  a panel whose refresh modes are FULL at ~770 ms on X3, HALF at 1720 ms, and
  FAST as a ghosting differential waveform
  ([HalDisplay.h:14](../../../lib/hal/HalDisplay.h)).
- **The general bar.** Nothing that assumes 50–60 fps can work here. Only
  turn-based play can.

Flash is not the constraint: the app partition is 6.4 MB at ~85%, leaving
roughly 960 KB. The binding constraints are RAM, display physics, and input.

### Why 2048 specifically

It is turn-based (one refresh per move), its entire state is 16 cells, and its
four directions map exactly onto the four screen-direction buttons the input
layer already rotates per orientation.

## Architecture

Four units, each independently understandable and testable.

| Unit | Path | Responsibility | Depends on |
|---|---|---|---|
| Game logic | `lib/Game2048/Game2048.{h,cpp}` | Board, slide/merge, spawn, win/over detection | nothing (host-buildable) |
| Layout | `src/components/themes/Game2048Layout.h` | `constexpr` board geometry from viewport dims | `Rect` only |
| Activity | `src/activities/games/Game2048Activity.{h,cpp}` | Lifecycle, input, rendering | HAL, GUI, the two above |
| Save store | `src/Game2048Store.{h,cpp}` | `/.crosspoint/2048.json` | `PersistableStore<T>` |

The split exists for one concrete reason: merge logic is the only genuinely
bug-prone part of 2048, and separating it makes it testable on the host in
milliseconds instead of on hardware.

### Unit 1 — `Game2048`

```cpp
class Game2048 {
 public:
  static constexpr uint8_t SIZE = 4;
  static constexpr uint8_t CELLS = SIZE * SIZE;

  enum class Direction : uint8_t { Left, Right, Up, Down };
  enum class Status : uint8_t { Playing, GameOver };

  // Injected RNG: esp_random on device, seeded counter in tests.
  using RandomFn = uint32_t (*)(void* ctx);

  void reset(RandomFn rng, void* ctx);
  bool move(Direction d, RandomFn rng, void* ctx);

  uint8_t exponentAt(uint8_t row, uint8_t col) const;  // 0 = empty, else 2^n
  uint32_t score() const;
  Status status() const;
  bool hasWon() const;   // 2048 reached; play continues
  bool canMove() const;

 private:
  uint8_t cells[CELLS] = {};   // exponents, not values
  uint32_t currentScore = 0;
  Status currentStatus = Status::Playing;
  bool won = false;
};
```

**Exponents, not values.** A cell stores `n` for a tile of `2^n`, so the whole
board is 16 bytes. `2^17` = 131072 is past any reachable tile, so `uint8_t` is
never close to overflowing.

**`move()` returning `false` is load-bearing.** A move that shifts nothing must
not spawn a tile and must not trigger a refresh. Without this, every blocked
swipe costs a wasted e-ink frame — the most visible way this feature could feel
broken.

**No heap allocation anywhere in this feature.** There is therefore no OOM path
to handle, and nothing to free in `onExit()`.

Merge rule, stated precisely because it is the easy thing to get wrong: for each
line in the direction of travel, compact out gaps, then merge adjacent equal
pairs **once**, scanning from the leading edge, then compact again. A tile
produced by a merge cannot merge again in the same move.

### Unit 2 — `Game2048Layout`

`constexpr` geometry in a header, following
[MenuLayout.h:148](../../../src/components/themes/MenuLayout.h):

```cpp
namespace Game2048Layout {
struct BoardGeometry {
  int16_t originX, originY, tilePitch, tileSize;
};
constexpr BoardGeometry boardGeometry(Rect viewable);
constexpr Rect tileRect(const BoardGeometry& g, uint8_t row, uint8_t col);
}  // namespace Game2048Layout
```

Geometry lives here rather than inside `render()` so it can be unit-tested
against all four orientations. This deliberately avoids the duplication
anti-pattern in
[ClockOffsetActivity.cpp:117](../../../src/activities/settings/ClockOffsetActivity.cpp),
where the same layout arithmetic appears in three places.

### Unit 3 — `Game2048Activity`

```cpp
void onEnter();                 // load save; fresh board if absent/corrupt/over
void loop();                    // input -> move -> requestUpdate
void render(RenderLock&&);      // draw board, push frame
void onExit();                  // save once, if dirty
```

Members are the `Game2048`, a de-ghost countdown, and a dirty flag. Nothing else.

### Unit 4 — `Game2048Store`

A `PersistableStore<Game2048Store>` at `/.crosspoint/2048.json`, alongside
`settings.json`. Fields: the 16 exponents, the current score, the best score.

`PersistableStore` is used rather than hand-rolled file I/O because it keeps the
ArduinoJson template instantiations in one translation unit — the reason that
base class exists ([PersistableStore.h:11](../../../lib/Serialization/PersistableStore.h)).

Storing this in `AlmanacSettings` was considered and rejected: transient game
state does not belong in the user-preferences file or its migration path.

## Input and orientation

Directions come from `Button::ScreenUp/ScreenDown/ScreenLeft/ScreenRight`, which
`mapScreenDirection()`
([MappedInputManager.cpp:20](../../../src/MappedInputManager.cpp)) rotates onto
physical buttons according to the live renderer orientation. **This activity
contains no orientation switch of its own** — all four orientations are correct
by construction.

Touch swipes via `wasSwipe()`, gated on `hasTouch()`, since touch is not present
on every panel.

| Control | Action |
|---|---|
| Screen up/down/left/right, or swipe | Move |
| Back | Exit (saves) |
| Confirm | New game — via `ConfirmationActivity` when a game is in progress |

Front-button labels come from `mapDirectionalLabels()` so the hints bar stays
truthful under remapping.

## Data flow and threading

`loop()` runs on the main task and mutates the board. `render()` runs on the
render task ([ActivityManager.cpp:25](../../../src/activities/ActivityManager.cpp))
and reads it.

**No mutex is added.** [AlmanacSettings.h:322](../../../src/AlmanacSettings.h)
warns that locking a render path stalls it behind SD I/O and creates a
`storeMutex`/`storageMutex` ordering hazard. The same reasoning applies here and
is stronger: board cells are single bytes and the score is an aligned
`uint32_t`, both atomic on RISC-V, and `move()` completes in microseconds before
`requestUpdate()` is called. The worst case is a single frame drawn from mixed
state, corrected by the next refresh.

## Rendering

Standard 2048 encodes tile value in colour. On a 1-bit panel that is
unavailable, so value is carried by the number itself, with weight added at the
top end: tiles are `drawRoundedRect` outlines with a centred number, and tiles
of 128 and above additionally get a `fillRectDither(Color::LightGray)` wash so
the heavy part of the board reads at a glance. Font size steps down by digit
count so a six-digit tile still fits.

Header via `GUI.drawHeader(tr(STR_GAME_2048))`; score and best score in the
content area; `GUI.drawButtonHints` at the foot. All drawing goes through the
`GUI` theme macro and `renderer` primitives — no hardcoded fonts or positions,
no raw `800`/`480`.

### Refresh strategy

Following `displayWithRefreshCycle()`
([ReaderUtils.h:118](../../../src/activities/reader/ReaderUtils.h)):

- `FAST_REFRESH` on each move.
- `HALF_REFRESH` every 15th move and on game-over, to clear accumulated
  ghosting.

`FULL_REFRESH` is deliberately not used: no activity in the firmware uses it,
and [SleepActivity.cpp:188](../../../src/activities/boot_sleep/SleepActivity.cpp)
records that its 0xF7 waveform blinks. `HALF_REFRESH` is the established
de-ghosting mode.

A no-op move performs no refresh at all.

## Error handling

| Condition | Behaviour |
|---|---|
| No save file (first run) | Fresh board. `readDocFromFile` returns false silently by design. |
| Corrupt save | `LOG_ERR`, discard, fresh board. Never a crash. |
| Saved game already over | Fresh board; best score preserved. |
| Save write fails on exit | `LOG_ERR` and continue. A lost game does not justify blocking exit. |

The save is written **once, in `onExit()`**, guarded by a dirty flag — never
per move, per the SPIFFS write-throttling rule in `CLAUDE.md`.

eight coordinated sites, and [HomeActivity.h:62](../../../src/activities/home/HomeActivity.h)

4. `getMenuItemCount()` — `src/activities/home/HomeActivity.cpp:44`
5. `menuItems` in `render()` — `src/activities/home/HomeActivity.cpp:220`
6. `activateSelection` switch — `src/activities/home/HomeActivity.cpp:116`

No build manifest change is needed: `[env:default]` sets no `build_src_filter`,
so anything under `src/` compiles automatically.

## Internationalisation

Five new keys, all of which were confirmed absent from `english.yaml`:

`STR_GAME_2048`, `STR_SCORE`, `STR_BEST`, `STR_GAME_OVER`, `STR_NEW_GAME`

Added to `lib/I18n/translations/english.yaml` only; the other 30 languages fall
back to English. Generated headers are produced by
`python scripts/gen_i18n.py lib/I18n/translations lib/I18n/` and are gitignored.

All user-facing text uses `tr()`. Log messages stay hardcoded.

## Testing

**Host unit tests** — `test/game_2048/`, registered in `test/CMakeLists.txt`
following the `semver` pattern. Run via `pio run -t unit-tests`.

Game logic:

- `[2, 2, 4]` moved left is `[4, 4]`, not `[8]`.
- A tile produced by a merge cannot merge again in the same move.
- A move that shifts nothing returns `false` and spawns no tile.
- Score increases by the value of each merged tile.
- Game over only when no move exists in **any** of the four directions — a full
  board with an adjacent equal pair is still playable.
- `hasWon()` flips at 2048, stays true, and play continues — winning is not a
  terminal state, only `GameOver` is.
- Spawned tiles are 2 or 4 and land only on empty cells (deterministic under the
  seeded RNG).

Layout:

- The board fits within the viewable area in all four orientations at both panel
  resolutions.
- Tile rects do not overlap and are ordered consistently with `exponentAt()`.

**Simulator** — `pio run -e simulator -t run_simulator` for the visual pass:
tile legibility, dither wash at the high end, six-digit fit.

**Hardware** (owner, not agent): all four orientations, ghosting behaviour over a
long game, save/restore across a power cycle, and free heap unchanged versus
baseline.

## SCOPE.md amendment

The owner chose to add a third mission pillar rather than a narrow carve-out.
`SCOPE.md` changes as follows:

- **Mission** gains a third item alongside Read and Look up, covering diversions
  on the device.
- **Out of scope** loses "games" from the interactive-apps clause; calculators
  and notepads stay out.
- A hardware bar is written down in its place: a diversion must be turn-based,
  need no network, and add no steady-state RAM. This keeps the emulator answer
  documented rather than relying on memory.

This is the broadest of the options considered. It reframes what Almanac is, and
invites feature growth beyond one puzzle; the hardware bar is what remains to
gate that growth.

## Out of scope for this spec

Undo, a win/continue screen, statistics, board sizes other than 4x4, and any
second game. Each would be its own proposal against the amended `SCOPE.md`.
